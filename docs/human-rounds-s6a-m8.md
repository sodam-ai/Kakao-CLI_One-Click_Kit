# 사람이 함께 하는 확인 라운드 절차서 (S6a · 입력란 측정 · M8)

작성: 2026-11-13. 이 문서는 **절차서일 뿐이고 아무것도 실행하지 않습니다.** 코드와 시험(388개 통과)은 가짜 부품으로만 확인한 것이고, 아래 라운드는 실제 카카오톡 화면이 필요해서 사람이 승인해야 시작됩니다. 정본은 설계서 13.2·13.8·13.9 입니다.

## 지금 막혀 있는 이유 (확인 못 한 것 3개 + Ctrl+S)

| # | 확인 못 한 것 | 왜 중요한가 | 확인하는 라운드 |
|---|---|---|---|
| 1 | 입력란의 화면 위치(창 크기·배율별) | 틀린 곳을 클릭하면 엉뚱한 곳에 글이 들어갑니다. | 라운드 B (읽기만) |
| 2 | 창을 닫은 뒤 초안이 남는지, 창이 숨겨질 때 어떻게 되는지 | 쓰다 만 글 위에 덧붙여 보내거나 초안이 사라질 수 있습니다. | 라운드 C (M8 승인 필요) |
| 3 | 여러 줄·이모지 붙여넣기와 0.8초 대기 값 | 줄이 깨지거나 Enter 가 먼저 나가면 글이 잘려 보내집니다. | 라운드 C (M8 승인 필요) |
| 4 | `Ctrl+S` 가 키트 경로·현재 버전(26.9.2.5342)에서 저장 창을 여는지 | 이전 확인은 5337 에서 손으로 한 것뿐입니다. | 라운드 A (S6a) |

## 공통 규칙 (모든 라운드)

- 시험은 **나 혼자만 있는 방**에서만 합니다.
- 라운드마다 사람이 **"60초 시작"** 이라고 말해야 시작합니다. 말하지 않으면 AI 는 카카오톡에 아무것도 입력하지 않습니다.
- 시작하면 사람은 카카오톡 창을 **한 번 클릭**해 맨 앞으로 만들고 **손을 뗍니다**(키트는 창을 맨 앞으로 가져오지 못합니다. 설계서 13.8).
- 키보드·마우스를 만지면 안전장치가 멈춥니다. 멈추면 그 라운드는 거기서 끝이고, 다시 하려면 새로 "60초 시작" 입니다.
- 쓰는 키는 `Ctrl+S`, `V`, `C`, `F`, `Enter` 다섯 개뿐입니다. 새 키는 화면에서 확인한 뒤에만 허용합니다. `Ctrl+A` 는 "친구 추가" 창을 열므로 금지입니다.
- 클립보드에 이미지나 파일이 있으면 시작하지 않습니다(원래대로 되돌릴 수 없기 때문).
- 결과 화면은 파일로 저장하지 않습니다(저장소 밖 임시 캡처만, 올리지 않음).

## 라운드 A — S6a: `Ctrl+S` 한 번 (입력 1개)

1. 사전: 허용된 혼자 방의 채팅 창을 열어 둡니다. 창 제목이 방 이름과 글자 그대로 같아야 합니다.
2. 사람이 "60초 시작" → 카카오톡 창 클릭 → 손 떼기.
3. AI 가 입력하는 것은 **`Ctrl+S` 하나**입니다(제목 일치·맨 앞 확인 후). 그 뒤 화면을 읽어 저장 창이 열렸는지 봅니다.
4. 저장 창이 열렸다면: 파일 이름 칸에 `Ctrl+A` 없이 붙여넣기만으로 경로가 바뀌는지 봅니다. **안 바뀌면 키를 늘리지 않고 멈춥니다.**
5. 기록할 것: 열림/안 열림, 파일 이름 칸의 기본 선택 여부, 카카오톡 버전. 통과해도 **5342 를 검증 목록에 넣는 결정은 사람이 따로** 합니다.

### 라운드 A 실행 기록 (2026-11-14, 카카오톡 26.9.2.5342)

- 결과: `Ctrl+S` 1회 보냄 → 약 2초 안에 카카오톡 소속 새 창 `다른 이름으로 저장` 1개가 열림. 입력은 그 1개뿐이고 메시지는 보내지 않았습니다.
- 맨 앞으로 올리기: 이번에는 키트가 직접 시도했고 허용됨(사용자 클릭 없음). **표본 1회뿐이라 조건은 미확정**입니다. 설계서 13.8("사용자가 클릭")은 바꾸지 않습니다. 앞서 두 번은 맨 앞이 아니어서 입력 없이 안전하게 멈췄습니다.
- 4번(파일 이름 칸 붙여넣기 확인)은 **하지 않았습니다.** 클립보드를 건드려야 해서, 필요 여부를 사람이 정하기 전에는 진행하지 않습니다.
- 저장 창은 AI 가 닫지 않고 사람이 취소로 닫도록 안내했습니다(닫힘 여부는 확인하지 않음). **5342 를 검증 목록에 넣는 결정은 하지 않았습니다**(A·B·C 통과 뒤 사람 결정).

### 결정 기록: 클립보드 사용 (2026-11-14, 사람이 "허용"으로 결정)

- 범위: **라운드 테스트 중에만** 허용합니다. 상시 사용은 별도 결정입니다.
- 조건: 시작 전 내용 저장 → 사용 → 복원(`Clip.ps1` 의 `Use-TextClipboard`). 복원하지 못하면 즉시 중단합니다.
- 글이 아닌 내용(그림·파일·소리)이 클립보드에 있으면 코드가 `clip.nonText` 로 **사용 전에 중단**합니다(`Get-ClipboardSnapshot`). 그래서 시작 전에 비우거나 확인합니다.
- 클립보드 내용은 로그·문서에 남기지 않습니다.
- 이 결정은 라운드 C 시작 승인("M8 승인")이 아닙니다. A 의 파일 이름 칸 붙여넣기 확인(4번)도 이 결정으로 풀리지만, 하려면 새 "60초 시작"이 필요합니다.

## 라운드 B — 입력란 위치 측정 (입력 0, 읽기만)

1. 카카오톡 창 크기·모니터 배율을 기록합니다(이 키트의 기준 크기와 비교).
2. 창 화면을 메모리에서만 읽어(저장 안 함) 입력란 영역을 창 크기에 대한 비율로 계산합니다.
3. 창 크기를 바꿔서(사람이 직접) 비율이 유지되는지 두세 가지 크기에서 확인합니다.
4. 기록할 것: 크기별 비율과 클릭해도 되는 안전 범위. 이 값이 있어야 `FocusInput` 을 만들 수 있습니다.

### 라운드 B 실행 기록 (2026-11-14, 카카오톡 26.9.2.5342, 배율 100%·dpi 96)

- 방법: 키·클릭 입력 0. 창 화면을 메모리로만 읽고(저장 안 함) 아래쪽 흰 입력 영역의 높이를 숫자로만 기록. 창 크기는 AI 가 창 맞춤 호출로 바꿨다가 **원래 위치·크기(395,1460,380x640)로 복원**을 확인.
- 결과(창 380x640 기준): 입력 영역은 창 **아래에서 약 91~92px** 높이(위쪽 경계 y≈546, 비율 0.853). 같은 폭에서 높이를 800으로 키우면 아래에서 91~92px 로 **같은 높이 유지**(비율은 0.884 로 변함). 폭 600·높이 900 에서는 x 위치에 따라 116px 가 읽힘.
- 결론(가능성): 입력란은 **비율이 아니라 "창 아래에서 몇 px"로 고정**된 것으로 보입니다. 따라서 `FocusInput` 을 창 크기 비율로 만들면 큰 창에서 어긋날 수 있습니다. 아래 기준 픽셀 오프셋이 더 안전해 보이지만, 100% 배율 1개·표본 5개뿐이라 **확정이 아닙니다**(배율 125%·150% 미측정).
- 주의: 창이 화면 밖으로 걸치면 걸친 부분은 읽히지 않고 흰 칸으로 나와 측정이 틀어집니다(처음 두 시도가 그랬음). 측정은 창 전체가 화면 안에 있을 때만 유효합니다.
- 클릭해도 되는 안전 범위는 **아직 정하지 않았습니다**(클릭 입력을 하지 않았고, 새 클릭은 화면 확인과 승인이 필요).

### 라운드 P 실행 기록 (2026-11-14, 카카오톡 26.9.2.5342, 배율 100%) — 클릭 없이 붙여넣기 되는지

- 방법: `Ctrl+V` **1개만** 보냄(Enter 없음, 클릭 없음). 클립보드는 "사용 전 저장 → 사용 → 복원"(결정 기록 참고). 메시지는 보내지 않았습니다.
- 결과: 입력 영역의 어두운 점 1 → 191(+190). 사람이 `테스트방` 입력란에 시험 문구가 **들어간 것을 눈으로 확인**했습니다. 클립보드는 원래대로 복원(길이 27 → 27, 같음. 내용은 기록하지 않음).
- 의미(가능성): 방 창을 맨 앞으로 올리면 입력란에 이미 포커스가 있어, **클릭 없이 붙여넣기만으로 입력되는 것으로 보입니다.** 그러면 `FocusInput` 에 클릭 좌표가 필요 없을 수 있습니다.
- 한계: 표본 1회. 같은 방·같은 배율·같은 창 위치에서만 확인. 직전 읽기 전용 측정의 기준값(190)과 이번 기준값(1)이 달라, 그 사이 입력란 상태가 바뀐 원인은 확인하지 못했습니다. 맨 앞으로 올리기도 이번에는 성공했지만 조건은 미확정입니다.
- 뒤처리: 남은 초안은 AI 가 지우지 않고 **사람이 직접** 지우도록 안내했습니다(지운 것은 확인하지 않음).
- 5342 를 검증 목록에 넣는 결정은 하지 않았습니다.

#### 라운드 P 2차 (2026-11-14, 같은 조건)

- 1번째 시도는 안전장치가 "키보드·마우스 사용 중"으로 **입력 0개에서 멈춤**(클립보드도 건드리지 않음). 2번째 시도에서 `Ctrl+V` 1개 보냄(Enter·클릭 없음).
- 로그: 어두운 점 0 → 175, 클립보드 복원(길이 454 → 454, 내용 미기록). 사람이 입력란을 보니 `[kit-focus-test][kit-focus-test]` 로 **시험 문구가 두 번 연달아** 들어가 있었습니다(보낸 붙여넣기는 1번뿐).
- 해석(가능성): 1차 때 남은 초안이 실제로는 지워지지 않았고, 2차 붙여넣기가 그 **뒤에 덧붙었을 가능성**이 큽니다. 맞다면 ① 붙여넣기는 커서 위치에 들어가므로 입력란 포커스 근거는 오히려 강해지고, ② 시작 전 "어두운 점 0"이 **빈 입력란의 증거로 믿을 수 없음**이 드러납니다(0이었는데 초안이 있었음). 원인은 확인하지 못했습니다.
- 결론: 클릭 없이 입력되는 것은 2회 모두 일치. 단, "입력란이 비었는가" 판정을 이 픽셀 방식에 맡기면 안 됩니다. 라운드 C 4번(초안이 있을 때 덧붙는 사고)이 실제로 일어날 수 있다는 실물 증거이기도 합니다.

#### 정정: 어두운 점 세기는 "입력란이 비었는가/글이 들어갔는가"의 증거가 아님 (2026-11-14, 라운드 C 준비 중 확인)

- 같은 빈 입력란을 잰 값이 190·174(창이 앞에 있을 때로 보임)와 0·1(뒤에 있을 때로 보임)로 갈렸고, 읽기 전용으로 다시 재니 가장 어두운 점이 175 였습니다. 빈 입력란에 보이는 **회색 안내 문구(placeholder)** 가 점으로 세어진 것으로 보입니다.
- 가능성(미확인): 안내 문구의 진하기가 창 포커스에 따라 달라집니다. 그렇다면 위 P 1·2차의 "+190·+175"도 글자가 아니라 안내 문구 변화였을 수 있습니다. 두 번 모두 **사람 눈으로 입력된 것을 확인**했으므로 "클릭 없이 입력됨"의 근거는 사람의 확인입니다.
- 결정: 이 방식은 게이트로 쓰지 않습니다. 보내기 전후 확인은 **사람 눈**(스크린샷 포함)으로 합니다.

## 라운드 C — M8: 실제 보내기 확인 (**별도 승인 필요**)

실제 전송이 일어나므로 "60초 시작"과는 **별개로 사람이 "M8 승인"** 을 말해야 합니다. 혼자 방, 짧은 글 1개씩만 보냅니다.

1. 한 줄 글 1개 → 방에 나타나는지, 입력란이 비는지.
2. 여러 줄 글 1개 → 줄이 그대로인지.
3. 이모지가 든 글 1개 → 글자가 깨지지 않는지.
4. 보내기 직전 입력란에 초안을 써 둔 상태로 키트가 연 창을 닫았다 다시 열어 초안이 남는지(남으면 덧붙는 사고가 납니다).
5. 0.8초 대기 뒤 클립보드가 원래대로 돌아왔는지.

각 단계마다 결과를 확인한 뒤에만 다음으로 갑니다. 하나라도 어긋나면 그 자리에서 멈추고 `Ready` 를 켜지 않습니다.

### 라운드 C 1번(한 줄 전송) 실행 기록 (2026-11-14, 카카오톡 26.9.2.5342, 배율 100%, "M8 승인"은 이 1번만)

- 방법: 두 번에 나눠 사람이 중간에 눈으로 확인했습니다. 1단계 `Ctrl+V` 1개(Enter 없음), 2단계 `Enter` 1개. 클릭 없음. 클립보드는 1단계에서만 "저장 → 사용 → 복원". 시험 문구는 `[kit-send-test 1] 한 줄 전송 확인`.
- 처음 시도는 픽셀 게이트(위 정정)가 "초안 있음"으로 잘못 읽어 **입력 0개에서 멈춤**. 게이트를 없애고 사람 확인으로 바꿨습니다.
- 1단계: 클립보드 복원(길이 387 → 387, 같음, 내용 미기록). 스크린샷으로 입력란에 문구 **한 번만**, 전송 전 상태 확인(덧붙음 없음).
- 2단계: 처음 세 번은 안전장치가 "대상 창이 맨 앞에 있지 않습니다"로 **입력 0개에서 멈춤**(그중 한 번은 사람 클릭을 120초 기다렸으나 시간 초과). 4번째에 `Enter` 1개 전송, 막힘 없음.
- 결과(스크린샷): 방에 문구가 **한 번만**(오전 11:18) 올라왔고 입력란은 비어 안내 문구가 보임. **1번 통과.**
- 막힘 조사(키·클릭 입력 없음): 터미널이 앞에 있는 상태에서 방을 올리는 데 16ms(키트는 80ms 기다림 → "기다림이 짧아서"라는 가설은 이 표본에서 뒷받침 안 됨). 실제 2단계와 같은 순서의 리허설(Enter만 뺌)은 전부 통과했고 이후 1.2초간 포커스를 뺏기지 않았습니다. 세 번 멈춘 원인은 **재현되지 않아 미확인**(간헐적일 가능성).
- 한계: 표본 1회, 같은 방·배율·창 위치. 창 올리기가 간헐적으로 실패할 수 있다는 점은 남음(코드 쪽 재시도 보강 후보). 아직 안 한 것: 2번(여러 줄), 3번(이모지), 4번(초안 유지), 5번(전송 후 클립보드 복원 확인). 5342 검증 목록 추가는 결정하지 않았습니다.

## 라운드가 모두 통과한 뒤에 코드에서 바뀌는 것 (그 전에는 바꾸지 않음)

- `Get-DefaultSendProvider` 의 `Ready` 를 측정·확인된 조건에서만 `$true` 로(한 줄 스위치가 아니라 조건 함수로).
