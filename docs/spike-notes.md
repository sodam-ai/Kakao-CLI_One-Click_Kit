# 스파이크 기록 (이 PC: Windows 11, 화면 언어 en-US, PowerShell 5.1)

각 작업의 "먼저 확인할 것"의 결과를 사실만 적는다. 틀린 가정은 후퇴 방안과 함께 적는다.

## Task 1 — 한글 깨짐 (2026-10-27)

**결과: 문제 없음.** 조건을 지키면 한글이 정상으로 보인다.

- `.bat`/`.cmd`: UTF-8 **BOM 없음** + CRLF, 두 번째 줄에서 `chcp 65001 >nul`. (첫 줄 `@echo off`는 ASCII라 안전)
- `.ps1`: UTF-8 **BOM 포함**. BOM이 없으면 PowerShell 5.1이 한글을 cp949로 읽어 깨진다.
- `src/kakao.ps1` 맨 위에서 `[Console]::OutputEncoding`을 UTF-8(BOM 없음)로 맞춘다. 상위 프로그램이 UTF-8로 읽으면 한글이 그대로 온다.
- 이 PC의 기본 터미널은 **Windows Terminal**이다. `cmd /c start "" 시작.bat`으로 연 창에서 한글(`카카오톡 키트`)이 정상 표시됨을 그 창만 캡처해 눈으로 확인했다(캡처는 삭제).
- 관리자 권한(UAC) 창은 뜨지 않았다.
- **함정:** `pause`는 시스템 언어(영어)로 "Press any key to continue . . ."를 출력한다. 요구 ②(영어 메뉴 금지)에 어긋나므로 `echo 한글 안내` + `pause >nul`로 바꿨다. 메뉴(Task 11)에서도 `pause` 단독 사용 금지.
- 한글 파일 이름(`시작.bat`)은 `cmd /c`와 PowerShell `Start-Process`에서 그대로 열린다.

## Task 4 — Win32 입력 계층 (2026-10-27)

**결과: 진짜 Win32 호출이 가짜 제공자와 같게 동작한다(읽기 전용으로 확인, 입력은 보내지 않음).**

- `EnumWindows`로 카카오톡 프로세스의 보이는 최상위 창 3개를 읽었다: 비밀방 채팅 창(제목이 방 이름과 **정확히 일치**), 메인 창(`카카오톡`, 4글자), 제목 없는 작은 창 1개. 클래스는 모두 `EVA_Window_Dblclk`. 제목 없는 창은 `ExpectedTitle`이 비어 있지 않은 한 가드를 통과할 수 없다.
- 보조 모니터의 **음수 좌표**(예: 왼쪽 -2174)도 `GetWindowRect`로 정상 읽힘. 클릭 좌표는 `왼쪽 + 비율 × 너비`로 계산하므로 음수 좌표에서도 동작한다.
- `GetLastInputInfo` 기반 "사람 손 감지"는 시험에서 가짜로만 검증했다. 진짜 입력을 보낸 직후 값이 바뀌는 정도(오탐)는 Task 8의 E2E에서 확인한다. 오탐이 잦으면 보내기 직후 30ms 대기값을 늘린다.
- **PowerShell 함정:** 명령 인자 자리에 쓴 `0x0002` 같은 16진수는 숫자가 아니라 문자열로 넘어간다(변수로 넘긴 값은 정상). 마우스 이벤트 값은 변수에 담아 넘긴다.
- 시험(`KAKAO_KIT_HOME`)은 진짜 키트와 같은 뮤텍스를 쓰지 않도록 잠금 이름에 경로를 붙인다.

## Task 7 — M7 스파이크, 카카오톡 26.9.1.5339 (2026-10-29~30)

위 Task 1·4 기록은 26.9.0.5337 기준이다. 아래는 26.9.1.5339 에서 키트 코드로 확인한 것이며 5337 기록은 지우지 않는다. 창 제목·닉네임·다른 방 이름은 적지 않는다.

**결과: S1 통과, S2 는 1회차 가드 정지 후 2회차 통과, S3(3a·3b) 통과.**

- S1(2026-10-29, 입력 0): 카카오톡의 보이는 최상위 창 4개를 0.11초에 읽었다. 클래스는 모두 같다(`EVA_Window_Dblclk`).
- S2 1회차(2026-10-29): 가드가 클릭 전에 상태 5(다른 키 눌림)로 정지했고 입력은 0이었다. 원인은 한/영 키(VK 0x15)가 손을 떼도 계속 눌린 것으로 읽힌 것(20번 중 20번). 눌린 키 검사에서 이 키만 제외해 고쳤다(PR #4).
- S2 2회차(2026-10-30, 이 PC): 클릭 1번과 붙여넣기 1번이 가드 정지 없이 통과했다(4.1초). 시작 전 포그라운드는 터미널이었고 가드의 맨 앞 확인을 통과했다.
- 캡처 2장(메인 창 588x753 px, 배율 150%, 오픈채팅 탭)으로 판정: 클릭(창 크기 대비 가로 0.714·세로 0.116)으로 검색창이 열렸고, 붙여넣은 방 이름이 정확히 입력되었으며, 검색 결과는 정확히 1줄이었다. 전송·입력 모드 전환·엉뚱한 입력의 흔적은 보이지 않았다.
- 한계: 앵커는 이 창 크기·배율·탭 조건에서만 확인했다. SendInput 으로 확인한 키는 Ctrl+V 하나이고 Enter·Ctrl+S·Ctrl+A·Ctrl+C 는 아직이다. 검색창에 방 이름이 남는다(지우는 허용 키가 없어 사용자가 직접 지움). 시험 방 창이 이미 열려 있었다(키트가 연 것 아님).
- 시험 방 변경(2026-10-30, 사용자 결정): 사용자가 이 프로젝트 전용 오픈채팅방(참여자 1명, 이름 "테스트방")을 만들었고 이후 시험은 이 방으로 한다. 위 S2 는 이전 시험 방으로 한 것이다.
- S3a(2026-10-30): 메인 창(오픈채팅 탭, 검색창 닫힘)에서 돋보기 클릭 1번과 "테스트방" 붙여넣기 1번이 가드 정지 없이 통과했다(2.9초). 캡처로 검색 결과가 정확히 1줄(테스트방, 참여자 1)임을 확인했다(흔한 이름이라 걱정했던 중복 방은 없었음). 클립보드는 전후 SHA-256 이 같아 정확히 복원되었다.
- S3b(2026-10-30): 방 창이 닫힌 상태에서 검색 결과 첫 줄(창 크기 대비 가로 0.45·세로 0.335)을 더블클릭하니 2.1초 만에 새 창이 열렸고 제목이 방 이름과 글자 그대로 같았다. 키트가 연 그 창에만 WM_CLOSE 를 보내 닫혔고(창 목록이 실행 전과 같은 2개로 돌아옴) 가드 정지는 없었다(전체 2.4초). 캡처는 쓰지 않았다.
- 한계: 첫 줄 앵커는 이 창 크기·배율·탭과 "결과가 정확히 1줄"인 상태에서만 확인했다. 방 창이 이미 열려 있을 때(재사용 경로), 결과가 여러 줄일 때, 검색창에 글자가 남는 점(지우는 허용 키 없음)은 아직이다. 방을 열면 읽음 처리가 되돌릴 수 없으므로 제품 코드는 열기 전에 결과가 정확히 1줄임을 확인해야 한다(한국어 OCR 은 아직 쓰지 않았고 이번에는 사람이 캡처로 확인함).
- 남은 것: 재사용 경로(선택), 열기 전 OCR 확인(`Ocr.ps1`), `Room.ps1` 구현(시험 먼저).
